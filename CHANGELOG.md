## Changelog Conventions

The changelog should describe noteworthy project changes in human-readable form rather than reproduce every Git commit.

Future entries may use categories such as:

- Added;
- Changed;
- Deprecated;
- Removed;
- Fixed;
- Security;
- Data;
- Scientific methodology;
- Architecture;
- and other categories appropriate to the change.

A change should be recorded according to what actually changed, not according to an intended but incomplete plan.

A future formal release entry should identify the actual release identifier and release date only after those facts exist.

## Scope

The changelog may record noteworthy changes involving:

- application capabilities;
- scientific-data handling;
- data schemas;
- provenance and uncertainty handling;
- source and license governance;
- architecture;
- APIs;
- user interfaces;
- accessibility;
- security;
- operational behaviour;
- modelling and simulation;
- documentation;
- and release engineering.

Routine internal edits that do not materially affect the project do not necessarily require a changelog entry.

Live earthquakes, volcanic events, tsunamis, or other continuously changing Earth-system observations are scientific or operational data and are not project changelog entries.

The changelog must not be used as a substitute for an event catalogue, hazard feed, scientific database, or provenance ledger.

## Accuracy and Traceability

Changelog statements must be supported by repository history or other authoritative project evidence.

Planned work must not be described as completed work.

Unreleased work must not be described as a published release.

Version identifiers and release dates must not be fabricated.

Where a changelog statement summarizes multiple underlying commits, the Git history remains the authoritative technical record of those commits.

Scientific claims and external-source provenance remain governed separately from repository change history.
